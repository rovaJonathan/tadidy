# TAD-030 — Keep the previous database key when a damaged file is reset

> Phase 1 · P2 · core · Discovered in: TAD-022 (fifth review of the pull request)

## Context

SQLCipher answers "file is not a database" both for a wrong key and for a damaged first page (a truncated file, a sync tool). TAD-022 maps both to `storage_wrong_key`, so a damaged file opened with the right key can be reset, and the reset overwrites the only key that decrypts the `.bak` file: even a repair tool could never read it. The spec says "No recovery is possible", so this is a product decision before it is a fix.

## Decision needed from the owner

- Accept the limit (the spec already says no recovery), or
- keep the previous key beside the backup (for example in a second Keychain account tied to the `.bak`), or
- replace the Keychain key only when it is missing, never when it exists but does not open the file.

## Scope

- The chosen option, with the reset's rollback rules unchanged.
- The spec's *Encryption* paragraph and the reset dialog's text, if the backup becomes recoverable.

## Out of scope

- A restore-from-backup flow.

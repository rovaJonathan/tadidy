# TAD-022 — Tell the user when the history database is unavailable and offer to reset it

> Phase 1 · P0 · full · Discovered in: TAD-016 (manual QA on the signed build: the popover showed an empty history and nothing recorded, because the signed app could not read the key that a dev build had stored in the Keychain; only a log line on stdout said so)

## Context

When `tadidy.db` exists but the Keychain has no key for it, `storage::open_or_report` logs `storage_key_missing`, the app runs **without a database**, and the watcher does not start (TAD-007, TAD-010). The user sees an empty history and nothing is ever recorded, with no explanation. The spec asks for the opposite: "If the key is missing while the database exists (Keychain reset), offer to **reset the history**. No recovery is possible." TAD-007 left that flow as future work. A stable signature makes it rare in production (Keychain access is tied to the code signature), but it happens as soon as a dev build and a signed build share `~/Library/Application Support/app.tadidy/`, and after a Keychain reset. The same applies to `storage_wrong_key` and to any other open failure.

## Scope

- **Status IPC**: `get_storage_status` returns `{ state: "ready" | "unavailable", code: string | null }` (the `AppError` code of the open failure, `null` when ready). Event `storage://changed` with the same payload, so every window updates when the state changes.
- **Reset IPC**: `reset_history_database` moves `tadidy.db`, `tadidy.db-wal` and `tadidy.db-shm` aside (renamed with a `.bak` suffix, **never deleted**; an older `.bak` is replaced only after the new move succeeded), creates a new key and a new database, starts the watcher, applies the stored settings, and announces `storage://changed` and `clips://changed`. It is refused (`AppError` `invalid_state`) when the database is `ready`, so it can never move a working history.
- **Front**: when the status is `unavailable`, the clip browser (popover and Quick Panel) shows an error state in place of the list and the empty state, with a **Reset history…** button; the button opens a confirmation dialog that states the history cannot be recovered, then calls `reset_history_database`. While `unavailable`, `list_clips` is not called and the footer shows no count.
- `AppState` can receive its database after startup (interior mutability on `db`), or the reset restarts the app: the choice is made in the plan and recorded in `PROGRESS.md`.
- The log line stays, and gains no path or key (AGENTS.md §2).

## Out of scope

- Recovering the old data, exporting it, or reading the `.bak` file back.
- A way to restore the `.bak` file from the UI.
- Telling the user that the shortcut may be shared with another app (TAD-017).

## Acceptance criteria

- [ ] Given a database whose key is missing from the Keychain, when the app starts, then `get_storage_status` answers `unavailable` with the code `storage_key_missing`, and no window calls `list_clips`.
- [ ] Given the status is `unavailable`, when the popover or the Quick Panel is shown, then an error state with a **Reset history…** button replaces the list, with no count in the footer.
- [ ] Given the confirmation dialog, when the user cancels, then nothing is moved or created.
- [ ] Given the confirmation dialog, when the user confirms, then the three database files are renamed with a `.bak` suffix, a new database and key exist, the watcher runs, and a clip copied afterwards appears in the list without restarting.
- [ ] Given a working database, when `reset_history_database` is invoked, then it is refused with `invalid_state` and no file moves.
- [ ] Given a failed reset (a file cannot be moved), then the status stays `unavailable`, the user can retry, and no file is lost.
- [ ] Given a log or an `AppError`, then neither contains a path under the user's home, a key, or clip content.

## IPC

- `get_storage_status() -> StorageStatus { state, code }`, `reset_history_database() -> ()`, event `storage://changed` (`StorageStatus`). Types derive `ts_rs::TS` ([ADR 0006](../docs/adr/0006-ts-bindings-with-ts-rs.md)); the front uses the generated bindings only.

## Security

- The database file is moved aside, never deleted, and the old key is never read or logged. Only an error code reaches the webview. The reset is confirmed in the UI, and refused by Rust when the database is healthy: a compromised webview cannot move a working history.

## Risks

- A `.bak` file keeps the old encrypted history on disk, unreadable without its key → documented in the dialog and the manual QA; no automatic purge.
- The watcher and the settings were set up without a database at startup → the reset starts them through the same code path as `setup`, covered by the integration test.
- Two windows hold the error state → both follow `storage://changed`.

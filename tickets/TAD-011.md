# TAD-011 — Settings store and history-size limit

> Phase 1 · P0 · core

## Context

The MVP preferences (General + Shortcuts) need a typed, validated, persisted settings object shared by Rust and the front. The first setting with behaviour is the history size (HIS-02, 500 by default): it must hold on every insert and immediately when the user lowers it. The preferences window (TAD-017) and the clip browser hosts (TAD-016) consume it.

## Scope

- `src-tauri/src/settings.rs`:
  - `Settings` (`#[derive(TS)]`, camelCase): `historySize: u32` (`0` = unlimited, otherwise ≥ 10; default 500), `confirmBeforeDelete: bool` (default `true`, HIS-05), `launchAtLogin: bool` (default `false`, SYS-01), `quickPanelShortcut: String` (default `"Cmd+Shift+V"`, QPN-01);
  - `SettingsPatch` (every field optional; ts-rs makes them `?:`);
  - `Settings::apply(&self, patch) -> Result<Settings, SettingsError>` with validation: `historySize` 1–9 rejected, empty shortcut rejected; `SettingsError` → `AppError { code: "invalid_settings", message }` naming the field.
- `src-tauri/src/storage/settings.rs`: one row per field in `settings` (key = field name, value = JSON); `load(conn) -> Settings` (missing or unreadable keys → defaults, unknown keys ignored), `save(conn, &Settings)` in one transaction.
- `AppState.settings: RwLock<Settings>`, loaded in `setup`; `HistoryLimit` (TAD-009) set from `historySize` at startup and on every change.
- IPC `get_settings() -> Settings`, `set_settings(patch: SettingsPatch) -> Settings`: validate, persist, update state, emit `settings://changed` with the new `Settings`; when `historySize` decreases, call `enforce_limit` at once and emit `clips://changed { removed }` if clips were deleted.
- Wrappers in `src/lib/api.ts`: `getSettings()`, `setSettings(patch)`, `onSettingsChanged(cb)`.

## Out of scope

- Applying `launchAtLogin` (autostart plugin) and re-registering `quickPanelShortcut`: TAD-017 (this ticket only stores and validates).
- P1 settings (expiry, pinned on top, sound, captured types, sizes, appearance…): added by their phase 2 tickets as new fields with defaults.
- The preferences UI (TAD-017).

## Acceptance criteria

- [ ] Given an empty `settings` table, when `get_settings` runs, then it returns `{ historySize: 500, confirmBeforeDelete: true, launchAtLogin: false, quickPanelShortcut: "Cmd+Shift+V" }`.
- [ ] Given `set_settings({ historySize: 5 })`, then it fails with `invalid_settings` and nothing is stored; `0` and `10` are accepted.
- [ ] Given `set_settings({ confirmBeforeDelete: false })`, then the returned and reloaded settings have it `false`, other fields unchanged, and `settings://changed` is emitted once with the full settings.
- [ ] Given 20 unpinned clips and `historySize` 500, when it is set to 10, then the 10 oldest unpinned clips are deleted, `clips://changed { removed }` lists them, and `HistoryLimit` returns 10.
- [ ] Given `historySize` 10 stored, when the app restarts, then `HistoryLimit` is 10 before the watcher's first tick.
- [ ] Given a stored row with an unknown key or invalid JSON, when settings load, then defaults are used for that field and no error reaches the user.

## Database

- No migration: rows in `settings` (0001), key = field name (`historySize`…), value = JSON.

## Security

- Settings hold no clip content; they are encrypted with the rest of the database anyway.

## Risks

- `historySize` "unlimited" needs a value → `0` means unlimited, the same convention as `HistoryLimit`; documented on the field (ts-rs doc comment).
- A decrease to 10 on a large history deletes many rows in one go → single transaction, then `incremental_vacuum`.
